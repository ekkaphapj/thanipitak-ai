## จำลองอะไรจากระบบจริง

อ้างอิงโค้ด `ekkaphapj/udonpolice-datacenter` ที่ `origin/main` commit `b1303e2` โดยเฉพาะ:

- `src/lib/psychiatricVisitResults.ts`, `drugVisitResults.ts`, `dealerStatus.ts`, `releasedPersonVisits.ts`
- `supabase/migrations/20260803090000_add_home_alert_summary.sql`
- `supabase/migrations/20260802130000_sticky_report_alert_until_officer_visit.sql`
- `supabase/migrations/20260802160000_per_color_report_thresholds.sql`

มีบุคคลสังเคราะห์ 80 คน แบ่ง 5 สถานี สถานีละ 16 คน, users 11 บัญชี และทะเบียนประเภท 9 รายการ จัดเป็น 4 กลุ่ม: จิตเวช ผู้เสพ ผู้ค้า ผู้พ้นโทษ

ตารางที่เพิ่ม: `people_type`, `people`, `guardian_reports`, `guardian_patient_links`, `person_report_status`, `guardian_report_settings`, `dealer_profiles`, `fixture_metadata` และเพิ่ม field ใน `visits`: `visit_time`, `visit_category`, `visit_status`, `status_condition`, `drug_test_result`

`people` เป็นทะเบียนตามรูปแบบจริง มีสีทะเบียนกับ custody_status แยกกัน ส่วน `persons` เป็นตาราง compatibility สำหรับ API เดิม สร้าง/อัปเดตผ่าน trigger จาก people โดยสถานะ active/completed ของตารางนี้เป็นค่ารองรับ API เก่า ไม่ใช่สีหรือระดับความเสี่ยงจริง หน้า AI แสดงสีทะเบียนและผลเยี่ยมจริงแยกกัน

พฤติกรรมที่ทำงานจริงใน simulation:

- เลือกผลเยี่ยมล่าสุดตามวันที่ เวลา และ ID ไม่ใช่ลำดับที่ใส่ข้อมูล; การเพิ่มบันทึกย้อนหลังไม่ทับผลล่าสุด
- แยก visit_category สำหรับจิตเวช ผู้เสพ และผู้พ้นโทษ
- การบันทึกผลตรวจผู้เสพสร้างประวัติผลปัสสาวะสำหรับ API เดิม
- ตรวจสิทธิ์สถานีก่อนอ่านและเขียน; viewer เขียนไม่ได้
- รายงานผู้ดูแลคำนวณจำนวนหมวดผิดปกติจากการพบตัว การกินยา อาการ และพฤติกรรม; รายงานยกเลิกไม่นำมาคำนวณ
- ระดับรายงานผู้ดูแลเพิ่มได้ แต่ไม่ลดเองจากรายงานปกติ; ผลเยี่ยมปกติล่าสุดของเจ้าหน้าที่ล้างสถานะค้างได้ การ refresh ภายหลังยังใช้รายงานและเกณฑ์ปัจจุบันตามกฎ
- สถานะออกนอกพื้นที่ เสียชีวิต อยู่ในเรือนจำ และยุติบทบาท ไม่อยู่ในคิวเฝ้าระวังในพื้นที่นี้
- แก้กรณี station scope ว่างใน personRepo ให้คืน 0 รายการ แทนการค้นทุกสถานี

## คำถามตัวอย่าง

- มีใครบ้างที่ต้องเฝ้าระวัง พร้อมเหตุผล
- ผู้ป่วยจิตเวชที่เสี่ยงสูงมีใครบ้าง เพราะอะไร
- ผู้ป่วยจิตเวชยาเสพติดที่เสี่ยงสูงมีใครบ้าง
- ผู้ป่วยจิตเวชอื่น ๆ ที่ต้องจับตามีใครบ้าง
- ขอรายชื่อผู้เสพที่ควรจับตาหน่อยครับ
- ผู้ค้ารายไหนต้องเฝ้าระวัง
- ผู้พ้นโทษความเสี่ยงสูงมีใครบ้าง
- ขอรายชื่อจิตเวชและผู้พ้นโทษที่ต้องเฝ้าระวัง
- Most Wanted ที่ต้องเฝ้าระวังมีใครบ้าง
- สรุปจำนวนคนกลุ่มเสี่ยงแยกตามประเภท
- ทำไมทดสอบ1 สถานี1ถึงเสี่ยงสูง
- คนนี้เสี่ยงสูงเพราะอะไร — เลือกบุคคลจากรายการก่อน
- เลือกบุคคลแล้วถามว่า เสี่ยงสูงเพราะอะไร — ตอบเฉพาะบุคคลที่เลือก แม้ไม่ได้พิมพ์คำว่า “คนนี้”
- หากผลลัพธ์มีเพียง 1 คน ระบบเลือกบุคคลนั้นเป็นบริบทให้เอง จึงถามต่อว่า “เพราะอะไร” ได้ทันที
- ขอรายชื่อ — แสดงรายชื่อในพื้นที่ที่มีสิทธิ์เข้าถึงทันที โดยไม่รอ Local AI
- ค้นหาตามภาษาพูด — ใช้ “ช่วยค้นหา”, “ค้นหา”, “หาบุคคล” หรือ “หาคน” แล้วตามด้วยประเภท ชื่อ จังหวัด/จ., สภ., อำเภอ/เขต, ตำบล หรือสถานะ เช่น “ช่วยหาผู้เสพในจังหวัดอุดรธานี อำเภอเมือง”, “หาคนชื่อสมชาย”, “ค้นหาผู้พ้นโทษที่ต้องติดตาม”
- ถ้าพิมพ์คำสั่งค้นหาโดยยังไม่บอกเงื่อนไข เช่น “ค้นหา” หรือ “หาคนชื่อ” ระบบตอบ “เงื่อนไขค้นหาไม่สมบูรณ์ กรุณาลองใหม่” โดยไม่เรียก Local AI
- สรุปแบบภาษาพูด — ใช้ “ช่วยสรุป” หรือ “สรุป” ร่วมกับจำนวน/รายชื่อ ประเภท ระดับ “ทั้งหมด/เฝ้าระวัง/เสี่ยงสูง” จังหวัด/สภ./อำเภอ/เขต/ตำบล และ “เรียงตามชื่อ”, “เรียงจากมากไปน้อย”, “เรียงจากน้อยไปมาก” เช่น “ช่วยสรุปจำนวนและรายชื่อผู้ป่วยจิตเวชที่เสี่ยงสูง เรียงตามชื่อ”
- พิมพ์ “ช่วยสรุป” หรือระบุพื้นที่ไม่ครบ ระบบแสดงปุ่มเลือกรูปแบบสรุปและรายการ สภ. อำเภอ ตำบลที่อยู่ในสิทธิ์ของผู้ใช้ หลังสรุปมีปุ่มและรองรับคำตอบ “ได้/ใช่/สร้างเลย” เพื่อสร้างรายงาน PDF สำหรับดาวน์โหลด
- เริ่มใหม่ — ล้างหน้าสนทนาและยกเลิกบุคคลที่เลือก โดยไม่ส่งคำขอไปยัง API
- เฝ้าระวังหรือเสี่ยงสูงมีใครบ้าง หน้า 2 — ใช้บัญชี admin เพื่อทดสอบ pagination

คำว่าเฝ้าระวังทั่วไปครอบคลุมทั้งเฝ้าระวังและเสี่ยงสูง ถ้าต้องการระดับเดียวใช้ “เฉพาะเฝ้าระวัง” หรือ “เสี่ยงสูง” รายบุคคลจะคืนระดับที่บันทึกจริง แม้คำถามใช้คำว่าเสี่ยงสูงแต่ข้อมูลเป็นเฝ้าระวัง เมื่อมีบุคคลถูกเลือกในหน้าแชต ระบบจะใช้บุคคลนั้นเป็นบริบทหลักของคำถามเฝ้าระวังและไม่ขยายเป็นรายชื่อรวม

คำถามย้อนช่วงเวลา/แบบยกเว้นที่ตรวจพบจะขอให้ระบุขอบเขตใหม่ ไม่ตอบยอดปัจจุบันแทนโดยเงียบ ๆ

## การไหลของ AI

`/api/ai/chat` → detectMonitoringIntent → get_monitoring_persons → monitoringService → ตารางที่ตรวจสิทธิ์แล้ว → ข้อความและ monitoring_list

คำถามที่รองรับตรงใช้ deterministic path จึงไม่เรียก Ollama ส่วนคำถามที่เข้า fallback มี tool `get_monitoring_persons` ให้โมเดลเลือก หลังได้ข้อมูล tool แล้ว backend render เหตุผลโดยตรง ไม่ให้โมเดลแต่งระดับหรือเหตุผลใหม่

ผลลัพธ์มี total ทั้งชุด, items ของหน้า, byType, page/pageSize, asOf และ reasons ที่ระบุ source/date/recordId มีปุ่มเลือกบุคคลถามต่อในแชต จำกัดหน้า 20 คน

อ่านผ่าน REST ได้ที่ `/api/monitoring` โดยใช้ Bearer token และ filter `person_type`, `level=all|watch|high`, `page`, `person_id` ไม่รับ station/role จาก query

## ข้อจำกัดที่ต้องรู้ก่อนต่อฐานจริง

ยังเป็น SQLite และจำลองเฉพาะส่วนที่ใช้เฝ้าระวัง ไม่ใช่ clone PostgreSQL/RLS ทั้งระบบ Auth ยังเป็น sandbox JWT และสิทธิ์ admin/officer/viewer ไม่ใช่ Supabase Auth หรือสิทธิ์ External/จังหวัด/ภาคของระบบจริง ตารางเกณฑ์ยังไม่มี override ตามกองบังคับการ และไม่มี guardian approval UI จริง

เกณฑ์ติดตามแบบ 30/60/15 วันใน API followup เดิมยังเป็น sandbox เดิม แยกจากระดับเฝ้าระวังใหม่นี้ บางหน้า dashboard ยังใช้สถานะ compatibility ของ API เดิม ควรทำ data/auth adapter และ integration test กับ staging ก่อนต่อ production

การอ่าน monitoring ปัจจุบันประเมินข้อมูลที่มีสิทธิ์ทั้งหมดก่อนแบ่งหน้า เหมาะกับ fixture ขนาดนี้ ยังไม่ได้ benchmark ฐานข้อมูลขนาดใหญ่
